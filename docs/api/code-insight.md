# Code Insight

Explanations of selected code, questions about a project, and each user's saved notes. **Service:** intelligence-service · **Controller:** `CodeInsightController` (`/api/projects/{projectId}/code`)

These paths sit under `/api/projects/**` but are routed to intelligence-service, not workspace-service: the Gateway gives `/api/projects/*/code/**` a higher priority. Every endpoint requires project `VIEW`.

**Read-only by construction.** The model is given at most one tool (`read_files`) and its prompts never mention the file-writing protocol, so nothing on this path can edit a project - including the "try changing this" task, which sends the person to make the change themselves with manual editing and only ever reads the result. See [AI prompt boundaries](../architecture/security-model.md#ai-prompt-boundaries).

**Written for the reader.** Every answering request may carry `level`: `"NEW"` (never coded - the default when it is absent), `"SOME"` (coded a little, new to React and TypeScript) or `"DEVELOPER"`. It chooses one of three fixed paragraphs of the prompt and nothing else; any other value is a `400`. The server does not store it.

| Method | Path | Request | Response | Notes |
|---|---|---|---|---|
| `POST` | `/code/explain` | `ExplainCodeRequest { path, code, startLine, endLine, level? }` | `{ answer }` | One-shot explanation of a selected block. `402` if the daily token budget is spent. |
| `POST` | `/code/ask` | `AskCodeRequest { path?, code?, question, history, level? }` | `{ answer }` | The selection is optional — omit it to ask about the project in general. The project's file paths (not contents) are always sent as context. `history` is replayed by the client (at most 40 turns); each turn's `role` is validated by value, and anything other than `"assistant"` is treated as a user message. Same budget check. |
| `POST` | `/code/explain/stream` | as `/code/explain` | SSE, plain text | The endpoint the UI uses. |
| `POST` | `/code/ask/stream` | as `/code/ask` | SSE, plain text | The endpoint the UI uses. |
| `POST` | `/code/lesson/stream` | `LessonRequest { eventId, level? }` - the id of a `FILE_EDIT` event in the caller's own chat on this project | SSE, plain text | Teaching mode's lesson on what one step of a saved turn changed, asked for when the person opens the step. Nothing but the id comes from the browser: the server reads the file as the turn saved it and the version it replaced from the event, and gives the model only the changed lines (new-file line numbers, a few lines of context; the whole file when the step created it), with what the person asked for and the turn's steps. The model gets no tool and answers with an opening, one `### L12-18 · Title` section per piece of the change, a closing `### What happens next`, and `### Check yourself` - one question the reader can answer from those lines. `404` if the event is not a file edit in the caller's own conversation on this project; `400` if its turn was not built in teaching mode. The finished lesson is stored on the event and returned as-is on every later call - no model call, no budget check - and is included in the chat history as the event's `lesson`. A stream that fails or is abandoned stores nothing. The call asks for low reasoning effort: a first real call at the default took 17 s to its first word and 24 s in all, and 4 s and 11 s at low. Same budget check as the others when a lesson has to be written. |
| `POST` | `/code/overview/stream` | `OverviewRequest { messageId, level? }` - the id of an assistant turn in the caller's own chat on this project | SSE, plain text | Teaching mode's big picture of a saved turn, shown before any step's lesson. Nothing but the id and the level comes from the browser: the server reads what was asked for, what the build said, its steps and the paths of the files it wrote from the saved turn. The model is given **no file text** - it reads the files it needs through `read_files` - and answers with an opening and the sections `### The pieces`, `### How it works` and `### Ideas in this build`. `404` if the turn is not an assistant turn in the caller's own conversation on this project; `400` if it was not built in teaching mode or wrote no file. The finished overview is stored on the turn and returned as-is on every later call - no model call, no budget check - and is included in the chat history as the turn's `overview`. A stream that fails or is abandoned stores nothing. Same budget check as the others when one has to be written. |
| `GET` | `/code/tour` | — | `{ content, writtenAt }`, or `204` when none has been written | The caller's own kept tour of this project. |
| `POST` | `/code/tour/stream` | `TourRequest { level?, rewrite? }` | SSE, plain text | "How your app fits together": a map of the whole project as it stands now. Nothing but the level and `rewrite` comes from the browser. The model is given the project's file paths and reads the files that make the app work through `read_files` (at most ten, in one call), and answers with an opening and `### The files`, `### How a click travels` and `### Where to change things`; the two to four programming words it uses are in **bold**, so the browser can open each in the glossary. Kept per project and per caller (`project_tours`); asked again, the kept text is returned as-is - no model call, no budget check - unless `rewrite` is `true`, which writes a new one over it once it has finished. `400` if the project has no files or they cannot be listed. A stream that fails or is abandoned keeps nothing, so a rewrite that fails leaves the old tour. Same budget check as the others when one has to be written. |
| `GET` | `/code/glossary` | — | `GlossaryEntryResponse[] { id, term, definition, createdAt }` | The caller's own glossary for this project, alphabetical. |
| `POST` | `/code/glossary/stream` | `GlossaryRequest { term, level? }` (`term` required, at most 200 characters) | SSE, plain text | One word's entry: a plain meaning, `### Think of it like` (an everyday comparison) and `### In your project` (a file where the word really shows up, a few lines from it, and what the word does there). The term is cut to one line and 80 characters with markup removed, reaches the model only as the word to define in a user message after the project's file list, and is matched without regard to case. A word already in the glossary is returned as kept, free. When the model says it is not a programming word, the answer is shown and nothing is kept. `400` for an empty term or when the caller already holds 200 words for the project. Same budget check as the others when an entry has to be written. |
| `DELETE` | `/code/glossary/{entryId}` | — | `204` | Removes one of the caller's own words; another member's id is a `404`. |
| `POST` | `/code/task/stream` | `TaskRequest { eventId, level? }` - the id of a `FILE_EDIT` event in the caller's own chat on this project | SSE, plain text | A small "try changing this" task set from one lesson's step: one tiny, safe change on a line that step added or rewrote, what to find there (`### L12 · Where to look`) and what the file must say once changed (`### Done when`). Found and bounded like a lesson - the model gets the same changed lines and no tool. `404`/`400` as for a lesson. Stored on the event (`chat_events.task`) and returned as-is afterwards, and sent with the conversation as the event's `task`. Same budget check when one has to be written. |
| `POST` | `/code/task-check/stream` | `TaskCheckRequest { eventId, level? }` | SSE, plain text | Checks whether the person has made the change. The model is given the file's path and the task - never the file's text - and reads the saved file through `read_files`; it answers `Done` or `Not yet` on the first line, then a few sentences. A `Done` marks the task done for good (`chat_events.task_done`, sent as the event's `taskDone`), after which the endpoint answers without a model call. `400` if the step has no task yet. Asked again on purpose after each `Not yet`, so it is not kept; each asking passes the budget check. |
| `GET` | `/code/notes` | — | `CodeNoteResponse[]` | The caller's own saved notes for this project, oldest first. |
| `POST` | `/code/notes` | `SaveCodeNoteRequest { question, answer, selection? }` | `CodeNoteResponse` | Saves one finished exchange. The client calls this after a stream finishes. |
| `DELETE` | `/code/notes/{noteId}` | — | `204` | Another member's note id is a `404`, not a `403` — the lookup is scoped to the caller, so it simply isn't found. |
| `DELETE` | `/code/notes` | — | `204` | Clears the caller's notes for this project. |

Notes are private: every query filters on both the project and the caller, so members of the same project never see each other's notes. So are the tour and the glossary, which are written for one reader's level and cost that reader's allowance.
