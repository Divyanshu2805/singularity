# Pitfalls: Spring and JPA

## `@PreAuthorize` parameter names must match exactly

- **Symptom:** a permission check denies every caller, including legitimate ones. No error at startup or compile time.
- **Cause:** the SpEL expression names a parameter that doesn't exist on the method — `#projectId` when the parameter is `id` — which evaluates to `null` and denies.
- **Fix:** check the parameter name character for character whenever you add or edit a `@PreAuthorize`. This has happened three times.

## A bean outside the component-scan root never exists

- **Symptom:** a `@Configuration`, `@Component` or `@Service` class's effect silently doesn't happen.
- **Cause:** the class sits outside its service's scan root (`com.singularity.<service>`), or it's in `common-lib`, which is not component-scanned at all.
- **Fix:** check the package matches the directory. For `common-lib`, register the class in `CommonLibAutoConfiguration`.

## `@Value` on a final field generated by Lombok

- **Symptom:** start-up fails with `No qualifying bean` for a class with a `@Value` field.
- **Cause:** `@FieldDefaults(makeFinal = true)` plus `@RequiredArgsConstructor` moves the now-final field into the generated constructor, but doesn't copy the `@Value` annotation, so Spring tries to inject a bean instead of a property.
- **Fix:** mark that field `@lombok.experimental.NonFinal`, or keep `@Value` fields out of the generated constructor.

## Flyway and Hibernate schema validation

- **Symptom:** a service refuses to start with "missing column", "missing table" or "checksum mismatch".
- **Causes and fixes:**
  - An entity has a field with no column → add a new `V<n>__*.sql` migration.
  - An applied migration was edited (Flyway checksums the whole file, comments included) → revert the edit and add a new migration.
  - Only `flyway-core` is on the classpath. On Spring Boot 4, Flyway's auto-configuration is in `spring-boot-starter-flyway`; without it Flyway never runs, and validation reports missing tables.
- **Never** add a `CHECK` constraint to an enum column. See [ADR 0006](../../architecture/decisions/0006-flyway-owned-schemas.md).

## Retrying a Spring AI stream

- **Symptom:** a retried AI stream throws instead of retrying.
- **Cause:** Spring AI's advisor chain is single-use per subscription, so `.retryWhen(...)` on an already-built `Flux` resubscribes to a spent chain.
- **Fix:** wrap the whole `chatClient.prompt()...` call in `Flux.defer(() -> ...)`, so every attempt builds a fresh chain.

## `save()` on a manually assigned id is an upsert

- **Symptom:** a uniqueness guarantee never triggers; two concurrent requests both "succeed".
- **Cause:** Spring Data treats an entity with a non-null id as existing and calls `merge()`, which updates or inserts and never fails on a duplicate.
- **Fix:** where an insert must detect a conflict, use a native `INSERT … ON CONFLICT … DO UPDATE … WHERE …` (`WebhookEventRepository.tryClaim`, `CheckoutIntentRepository.claimOrRefresh`).

## A Postgres function returning `void` in a native query

- **Symptom:** a repository method throws `ClassCastException` at request time — not at boot, and not in tests that mock the repository.
- **Cause:** `pg_advisory_xact_lock(...)` returns SQL `void`, which the JDBC driver returns as a `PGobject` that can't be cast to the declared return type.
- **Fix:** select a literal: `SELECT 1 FROM pg_advisory_xact_lock(...)` still takes the lock and returns a plain integer. See `ProjectMemberRepository.lockProjectQuota`.

## Removing an association breaks another entity's join columns

- **Symptom:** start-up fails with ``A '@JoinColumn' references a column named 'X' but the target entity has no property which maps to this column``.
- **Cause:** replacing a `@ManyToOne` / `@MapsId` association with a plain id column can remove the only property another entity's `@JoinColumns(referencedColumnName = ...)` resolved against.
- **Fix:** drop `referencedColumnName` from the referencing `@JoinColumns` and let Hibernate map the columns positionally against the target's composite id (as `ChatMessage` → `ChatSession` does).

## A bean cycle across three beans is invisible to unit tests

- **Symptom:** a service compiles and passes every test, then fails to start with a circular-dependency error.
- **Cause:** a cycle across several beans (`RevisionPublisherImpl` → `RevisionBuildValidator` → `RevisionServiceImpl` → `RevisionPublisher`) only appears when a full context wires them together, which no plain unit test does.
- **Fix:** extract the shared method into a leaf component both sides depend on (`RevisionSnapshotReader`). Always boot the service with `spring-boot:run` before calling a change done.

## Injecting a Feign client into a `@WebMvcTest` bean method

- **Symptom:** a `@WebMvcTest` fails with `NoSuchBeanDefinitionException: FeignClientFactory`, even though the Feign client is mocked.
- **Cause:** `@EnableFeignClients` registers a real proxy factory for every `@FeignClient`. A test `@Bean` method that *takes* that interface as a parameter makes Spring resolve every bean of the type — including the real proxy, which needs Feign auto-configuration the slice doesn't load.
- **Fix:** hold the mock in a field and construct the dependent bean directly, instead of asking Spring to inject the mock as a method parameter (see `FullChainChatAccessTest.TestSecurityBeans`).

## The Windows time-zone workaround is per service

- **Symptom:** a service (or a Spring-context test) fails its first Postgres connection on Windows with a time-zone error.
- **Cause:** the Windows JVM reports the legacy `Asia/Calcutta` zone, which PostgreSQL rejects. The fix is a JVM default set in `main()`, so it doesn't carry across services — and Spring's test support bypasses `main()` entirely.
- **Fix:** every service's `main()` calls `WindowsTimezoneWorkaround.apply()` before `SpringApplication.run(...)`. For a Spring-context test, call it in `@BeforeAll` or pass `-Duser.timezone=Asia/Kolkata`.

## A test instance per class starts the Spring context before Testcontainers

- **Symptom:** a `@Testcontainers` test with `@TestInstance(PER_CLASS)` fails to load its context with `Mapped port can only be obtained after the container is started`.
- **Cause:** with one instance per class, JUnit creates the instance - and Spring builds the context for it - before the Testcontainers extension's `beforeAll` has started the static containers.
- **Fix:** start the container by hand at the top of the `@DynamicPropertySource` method (`PreviewPipelineIT.connect`); `start()` is idempotent, so the extension finding it running is harmless.

## A `%` in a shell script built with `String.formatted`

- **Symptom:** a method that builds a script with a text block and `.formatted(...)` throws `UnknownFormatConversionException` at run time - not at compile time, and only on the path that builds that script.
- **Cause:** shell parameter expansion uses `%` (`${pid%/cmdline}`), which the formatter reads as the start of a conversion.
- **Fix:** write it `%%` inside a formatted block (`PreviewBootstrapper.resyncScript`), and leave scripts that take no arguments unformatted.

## `@Modifying(clearAutomatically = true)` throws away changes that were only queued

- **Symptom:** a delete or an update "succeeds" - the request answers 204, nothing is logged - and the row is unchanged. It happens only on some paths: removing a member who had the preview open, leaving or deleting a project whose preview was running.
- **Cause:** `repository.delete(entity)` and `save(entity)` queue their SQL until the transaction flushes. A `@Modifying(clearAutomatically = true)` query later in the same transaction clears the persistence context when it finishes, queued work included, and Hibernate does not flush first unless the query touches the same table. Every preview status update is such a query.
- **Fix:** `flush()` the change before calling anything that may run one (`ProjectMemberServiceImpl.removeProjectMember`, `ProjectServiceImpl.softDelete`). A unit test with mocked repositories cannot see this; the tests pin the order - written, then flushed, then the preview call - and the proof is the SQL log showing the `delete`.

## A revision snapshot is not the whole project

- **Symptom:** restoring an earlier version (or undoing a turn) would delete `package.json`, `index.html` and the component kit. Unit tests of the restore passed. It was caught by reading the code when the History panel was built, before any restore had been run; nothing had called the endpoint until then.
- **Cause:** the starter template's files and a fork's copied files are written with no revision, so `RevisionSnapshotReader.snapshot` holds only the paths some revision has changed. Diffing the current files against that alone reads every untouched file as "added since" and a template file first changed later as "did not exist yet".
- **Fix:** a restore target is the snapshot laid over each path's original content (`ProjectFileRevisionRepository.findOriginalContent`), and a current file with no content hash is left alone (`RevisionServiceImpl.stateFor`). Anything else that needs "the project as of revision N" must do the same; the snapshot reader by itself is only right for a project every file of which has been through a revision.

## Find-then-save is two requests' worth of "not found"

- **Symptom:** a first sign-in from two tabs at once answers one of them with a `500`; the account exists and the next attempt works.
- **Cause:** both requests looked the user up, found nobody, and inserted. The second insert broke the unique Firebase uid, and nothing read that as "someone else just made it".
- **Fix:** catch the `DataIntegrityViolationException`, read the row again, and carry on as the existing user; rethrow when the row still is not there, since then it was a different violation (`SessionServiceImpl.resolveAccount`). Where there is no row to fall back on, use a native upsert instead (`ProjectInviteRepository.upsert`).

## Security headers written while a streamed response has already begun

- **Symptom:** now and then a chat or lesson stream is a `500` before it starts; the service's log has `ArrayIndexOutOfBoundsException` inside Tomcat's `MimeHeaders`, under `HeaderWriterFilter`, and the Gateway reports `Connection prematurely closed BEFORE response`. It needs several streams starting at the same moment - eight first builds at once did it - so one person clicking never sees it.
- **Cause:** Spring Security writes its response headers when the filter chain returns or when the response is committed, whichever is first. For a streamed response those are two threads: the request thread leaving the chain and the stream's own thread writing its first event. Both touch the response's header table, which is not built for that.
- **Fix:** every browser-facing chain writes the headers before the request is handled (`EagerSecurityHeaders`, applied in `ServiceSecurityConfig` and account-service's `WebSecurityConfig`), so only the request thread ever writes them. A new `SecurityFilterChain` must do the same; the `FullChain*AccessTest`s check it. Found by the load test (`e2e/load.mjs`), not by any unit test - a race like this needs a real container and real concurrency.
